Claude Codeの日本語入門ガイドを公開したあと、しばらくして内容を読み直すと、文章は自然でも説明が現在の仕様と合わない箇所が増えていました。

インストール方法、コマンド、権限モード、MCP、Hooks、サブエージェント、モデルや料金。Claude Codeのように更新頻度が高いツールでは、公開時に正しかった説明も、そのままでは古くなります。

そこで、[CC101日本語版](https://cc101jp.vercel.app/ja)を2026年10月時点の情報へ更新しました。対象にした基準点はClaude Code v2.1.301です。この記事はその時点の更新作業の記録であり、現在のClaude Codeの全仕様を説明するものではありません。

- [更新コミット](https://github.com/im-jaehong/cc101jp/commit/dc21edf1d92a994c5f3d12e05791243763d0b37d)
- [GitHub: im-jaehong/cc101jp](https://github.com/im-jaehong/cc101jp)

この記事では、翻訳済みの技術資料をどのように棚卸しし、AIを使いながらも公式情報を基準に更新したかをまとめます。

## 「日本語として読める」と「現在も正しい」は別だった

最初の日本語化では、原文の意味を崩さず、初心者にも読みやすい文章へ移すことを重視しました。しかし、時間が経つと別の問題が現れました。

たとえば、次のような説明は変化の影響を受けやすい部分です。

- 推奨されるインストール方法
- 対応OSとWindowsでのシェルの扱い
- 利用できるスラッシュコマンド
- 権限確認や安全機能の動作
- MCP、Skills、Hooks、サブエージェントの設定方法
- モデル名、コンテキスト長、料金
- 廃止・名称変更されたオプション

文章の誤訳なら原文と比較して直せます。一方、原文そのものが古い場合、正確に翻訳するほど古い仕様を正確に伝えてしまいます。

この経験から、翻訳資料には少なくとも二つの品質が必要だと考えるようになりました。

1. 原文の意味を正しく移していること
2. 説明している事実が現在も有効であること

今回の更新では、2番目を中心に見直しました。

## 先に更新範囲を数字で確認した

感覚だけで修正を始めると、目についたページだけが新しくなり、言語間の差が広がります。そのため、最初にGitの差分を使って対象を把握しました。

2026年8月版から10月版への更新コミットを確認した結果は次のとおりです。ファイル数と行数は[当該コミット](https://github.com/im-jaehong/cc101jp/commit/dc21edf1d92a994c5f3d12e05791243763d0b37d)の差分、言語別のMarkdown数は同コミットのツリーから数えました。

| 項目 | 結果 |
|---|---:|
| 変更ファイル | 66ファイル |
| 追加 | 1,652行 |
| 削除 | 674行 |
| 対応言語 | 韓国語・英語・日本語 |
| 各言語のMarkdown | 21ファイル |

日本語だけを直したのではありません。`content/ko`、`content/en`、`content/ja`の同じ章を対応させ、セクション定義やREADMEも更新しました。

```bash
git diff --stat b7de8e97a6a733965e290c148c1f316d598bfa2a..dc21edf1d92a994c5f3d12e05791243763d0b37d
git diff --name-only b7de8e97a6a733965e290c148c1f316d598bfa2a..dc21edf1d92a994c5f3d12e05791243763d0b37d
```

この二つだけでも、「どの章を触ったか」「一言語だけ漏れていないか」を確認できます。

## 参照元に優先順位を付けた

AIへ「最新情報に直して」と依頼するだけでは、もっともらしいコマンドや存在しない設定が混ざる可能性があります。そこで、情報源に優先順位を付けました。

1. [Claude Code公式ドキュメント](https://code.claude.com/docs/en/overview)
2. [公式CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)
3. [Anthropic公式GitHubリポジトリ](https://github.com/anthropics/claude-code)
4. 実際にインストールした環境の`--help`や画面表示
5. ブログ、SNS、コミュニティ投稿

ブログやSNSは変更点を知るきっかけとして便利ですが、最終的な根拠にはしませんでした。特にコマンド、料金、対応OSは公式情報へ戻って確認しました。

公式情報同士でも、公開タイミングによって一時的に差が出ることがあります。その場合は無理に断定せず、「2026年10月17日時点」「v2.1.301で確認」のように確認時点を残します。

## 章ごとではなく、変化の種類ごとに調べた

21章を先頭から順番に読むだけでは、同じ仕様が複数ページに散らばっていることを見落とします。今回は、先に変化しやすい項目を一覧にし、それぞれが登場するファイルを検索しました。

```text
インストール
  ├─ macOS / Linux
  ├─ Windows / PowerShell
  └─ 更新方法

操作
  ├─ コマンド
  ├─ ショートカット
  └─ セッション管理

拡張
  ├─ MCP
  ├─ Skills
  ├─ Hooks
  └─ サブエージェント

運用
  ├─ 権限と安全性
  ├─ 自動化
  └─ コスト
```

たとえば権限モードを変更した場合、基本概念の章だけでなく、コマンド一覧、トラブルシューティング、自動化、Hooksの説明にも影響します。項目単位で検索することで、同じ用語が別の説明のまま残ることを減らせました。

## AIには「調査結果の整理」と「三言語の同期」を任せた

今回もClaudeとChatGPTを利用しました。ただし、AIの回答をそのまま仕様として採用するのではなく、役割を限定しました。

### AIに任せたこと

- 既存文書からバージョン依存の記述を抽出する
- 公式ドキュメントと差がありそうな箇所を一覧化する
- 同じ変更を韓国語・英語・日本語へ展開する
- 用語の揺れや重複説明を探す
- 長い差分を章ごとに要約する

### 人が確認したこと

- 参照URLがAnthropicの公式情報か
- コマンドやオプションが実在するか
- バージョンやプランによる違いを混同していないか
- Windowsの説明がWSL、Git Bash、PowerShellのどれを指すか
- 日本語が自然でも技術的な意味を変えていないか
- 更新後のサイトを実際にビルドできるか

AIへは、単に「修正して」ではなく、根拠となるURLと確認日をセットで出すように依頼しました。根拠が見つからない変更は保留にします。

複数のAIが同じことを回答しても、同じ古い情報を参照している可能性があります。AI同士の一致は補助材料であって、一次情報の代わりにはなりません。

## 三言語を同時に更新するときのルール

三言語対応では、文章を個別に直すだけでは不十分でした。次のルールを決めました。

### コマンドは翻訳しない

コマンド名、JSONのキー、ファイルパス、環境変数は、説明文と分けて扱います。自然な日本語に見せるためにコードを翻訳すると、利用者がそのまま実行できなくなります。

### 一つの言語だけに情報を足さない

日本語で補足が必要になった場合でも、事実に関する変更なら韓国語と英語にも反映します。日本固有の説明であれば、その理由が分かるようにします。

### 同じ用語は同じ意味で使う

Permissionを「許可」「権限」「承認」とページごとに変えると、初心者には別の概念に見えます。翻訳の自然さより、ガイド全体での一貫性を優先しました。

### 日付を隠さない

モデル名や料金のように変化が速い情報には、確認時点を付けます。「最新」とだけ書くと、いつの最新情報か分かりません。

## 最後は文章ではなく、成果物を検証した

Markdownが読めても、コードやメタデータが壊れていれば公開できません。更新後は次の確認を行いました。

```bash
git diff --check
pnpm lint
pnpm exec tsc --noEmit
pnpm build
```

更新作業当時の記録では、ESLint、TypeScript、Next.jsのプロダクションビルドが通り、`/ko`、`/en`、`/ja`が静的ページとして生成されたとしています。この記事の公開前レビューではコミットの差分とファイル構成を再確認しましたが、当時のビルド環境でこれらのコマンドを再実行してはいません。

加えて、次の項目は検索と画面確認で調べました。

- 古いコマンド名が残っていないか
- 旧ドメインがメタデータに残っていないか
- 三言語で章数が一致しているか
- 外部リンクが意図した公式ページを指しているか
- Footer、OGP、ライセンス表記が現在のプロジェクトに合っているか

ここで、本文を更新してもOG画像やドメイン表記は自動では変わらないことに気付きました。文書の保守とサイトの公開設定は、同じチェックリストで確認した方が安全です。

## 更新して分かったこと

### 1. 技術資料は完成品ではなく、バージョン付きの成果物である

「Claude Code入門ガイド」とだけ書くより、「2026年10月17日、v2.1.301を基準に確認」と書く方が読者にとって親切です。更新後に仕様が変わっても、誤りの発生地点を追いやすくなります。

### 2. 変化しやすい情報は分離した方がよい

料金、モデル一覧、コマンド一覧を複数の章へ直接書くと、更新漏れが起きます。将来的には一か所のデータから表示するか、少なくとも検索しやすい表現へ統一したいと考えています。

### 3. 翻訳AIより、検証の設計が重要だった

長い文章の翻訳や三言語への展開はAIで速くできます。しかし、何を一次情報とするか、どの変更を保留するか、どこまでテストするかは人が決めなければなりません。

### 4. 初心者向けほど、曖昧な表現を残せない

経験者なら古いコマンドを見ても代替手段を探せます。初心者は、書かれた手順が動かなければそこで止まります。入門資料だからこそ、インストールや最初の操作を優先的に更新する必要があります。

## 今後の運用

次回からは、大規模な見直しだけに頼らず次の流れで運用します。

1. Claude Codeの公式CHANGELOGを定期的に確認する
2. 影響を受ける章をIssueまたはチェックリストへ記録する
3. 三言語を同じ変更単位で更新する
4. 確認日と基準バージョンを残す
5. lint、型検査、ビルドを通す
6. 公開後に実際のページとOGPを確認する

すべてのリリースへ即日追従することは現実的ではありません。初心者が最初に使う手順、安全性に関わる説明、廃止された操作を優先し、更新の重要度を分ける方針です。

## まとめ

日本語化した時点では、翻訳が終われば教材も完成すると考えていました。しかし実際には、技術資料は公開後から保守が始まります。

今回の更新では、公式ドキュメントとCHANGELOGを基準に、66ファイル、三言語の内容を見直しました。AIは調査候補の抽出や翻訳の同期に役立ちましたが、採用判断と最終確認は一次情報と実際のビルドを基準にしました。

「最新のガイド」を作ることより、「いつ、何を基準に確認したガイドか」を説明できることの方が重要です。次の更新で差分を追える状態まで含めて、技術文書の品質だと学びました。
