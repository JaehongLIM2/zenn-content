休止状態から復帰して、YouTubeやローカル音楽を再生するWindows用アラームを個人開発しています。

[前回の記事「知人の家のテレビを見て、テレビのない自宅にWindowsアラームを作った」](https://zenn.dev/nu0044/articles/windows-alarm-tv-inspired)では、テレビの予約電源をきっかけに、手元のPCでアラームを作り始めた経緯を書きました。

前回、続編で扱うと書いたのが、音声出力の切り分けとUIの見直しです。今回はUIの方を取り上げます。開発中にボタンの角やフォントを整えていくと、見た目より先に整理したい疑問がありました。

**「Wake Timerの取り消し」は、何を止めるボタンなのか。**

開発中のやり取りでも、これが次回のアラームを取り消す操作なのか、自動終了を取り消す操作なのかを確認し直しました。自分で作りたいと考えたアプリなのに、表示されている名前から動作をすぐに判断できていませんでした。

今回は、ボタンの名前と配置を変えるところから、予約状態と取消操作の関係を見直した記録です。[Windows Alarmのリポジトリ](https://github.com/JaehongLIM2/alarm_program)を公開しており、本文では[画面表示の判定](https://github.com/JaehongLIM2/alarm_program/blob/86faa68bdd246ec04025ffa1583b27d90b42164b/src/WindowsAlarm/Services/ReservationStatus.cs)と[予約取消の処理](https://github.com/JaehongLIM2/alarm_program/blob/86faa68bdd246ec04025ffa1583b27d90b42164b/src/WindowsAlarm/Services/AlarmCoordinator.cs)も参照できます。

## 「停止」と「取消」が、それぞれ何に作用するのか

このアプリには、音を止める操作と、未来の動作を取り消す操作があります。

たとえば、7時30分にアラームを開始し、その30分後に自動終了の確認を始める設定を考えます。

```text
07:30  アラーム開始
          ↓
07:35  音を停止
          ↓
08:00  PC自動終了の確認を開始
          ↓
        利用状況に応じてカウントダウン、または明示的な終了確認へ
```

7時35分に音を止めても、PCの自動終了予約は残ります。音を止めることと、PCの終了を取り消すことは別の操作にしています。

利用を検出した場合や活動情報を信頼できない場合には、応答がなければ自動終了を取り消す既存の保護があります。この例で、音を止めたあとにPCが必ず終了するという意味ではありません。それでも、音を止める操作だけでは終了予約を取り消した状態にはなりません。

この違いは、内部の処理を知っていれば分かります。しかし、画面上で単に「停止」「取消」と並んでいると、どこまで止まったのかを確認しにくくなります。

そこで、まず操作の対象を整理しました。

| 操作 | 現在の画面上の表示名 | 作用する対象 |
| --- | --- | --- |
| アラーム停止 | `알람 정지` | 再生中の音声。自動終了予約は残す |
| アラーム予約の取消 | `알람 예약 취소` | まだ開始していない次回アラーム。その予約に付く自動終了も無効にする |
| PC自動終了の取消 | `PC 자동 종료 취소` | そのアラームに伴うPC自動終了。音声の停止とは独立した操作 |

以前の`Wake Timer 취소`は`알람 예약 취소`に、`예약된 자동 종료 취소`は`PC 자동 종료 취소`に変更しました。

実装上はWindowsのWake Timerを扱っていても、操作する側が知りたいのは「次のアラームが取り消されるのか」です。また、「自動終了」の対象がPCだと分かるようにしました。

音を停止するボタンの近くにも、**自動終了予約は維持される**と明記しています。音声停止時には、選択した停止後の音量設定も適用します。一方、PC自動終了の取消だけでは音声や音量を変えません。名前に加えて、操作後に何が残るかを説明する必要がありました。

## 予約状態と取消ボタンを隣に置く

以前の下部には、予約の取消、ログ、電源状態の確認、フォントライセンスといったボタンが並んでいました。一方、予約状態の表示は、設定と同じスクロール領域の下にありました。

個々の機能はあっても、「今の状態を確認する場所」と「その状態を変更するボタン」が離れていました。

画面を次の配置に変えました。これは配置の模式図で、実画面のスクリーンショットではありません。

```text
Windows Alarm                  [電源状態を確認] [⋯]

               設定領域
        時刻・再生内容・音量・自動終了
             この領域をスクロール

────────────────────────────────────
アラーム予約  2026-10-28 07:30       [予約を取消]
PC自動終了    アラーム開始30分後に確認 [自動終了を取消]

                処理結果・エラーの表示

[       アラームをテスト       ] [     設定を保存     ]
[           アラームを設定して休止状態にする           ]
```

下部は固定し、予約の状態と、それを取り消す操作を一組にしました。通常の設定操作はその下にまとめ、休止状態に入るボタンは全幅にしています。

電源状態の確認は上部に置き、ログ・プログラム情報・フォントライセンスは「⋯」メニューに移しました。PC自動終了の取消はこのメニューに入れていません。終了が近づいているときに、メニューを探してから取り消す操作にはしたくなかったためです。

図の2行は、常に表示するわけではありません。該当する予約がなければ、行全体を隠します。

## 表示の基準を、入力欄ではなく予約済みの状態にする

予約があるときだけ表示すると決めたあと、何を見て「予約がある」と判断するかを整理しました。

このアプリは、予約時の設定をスナップショットとして保存します。その後に入力欄や自動終了のトグルを変更しても、既存の予約が書き換わるわけではありません。設定の保存と、予約のやり直しも別の操作です。

そのため、自動終了トグルの現在値だけで取消ボタンを隠すと、次の状態を作ってしまいます。

```text
自動終了ありでアラームを予約
  ↓
画面の自動終了トグルをオフに変更
  ↓
予約済みの自動終了は残っている
  ↓
それなのに取消ボタンだけが消える
```

これを避けるため、表示には実際の予約スナップショットと、自動終了を管理するコントローラーの状態を使っています。

| 状態 | アラーム予約の取消 | PC自動終了の取消 |
| --- | --- | --- |
| 予約なし | 表示しない | 表示しない |
| 未来のアラームを予約・自動終了なし | 表示する | 表示しない |
| 未来のアラームを予約・自動終了あり | 表示する | 表示する |
| 音を停止したが、自動終了は待機中 | 表示しない | 表示する |
| 終了カウントダウン・利用中の確認待ち | 表示しない | 表示する |
| 取消処理が未完了 | 未完了の対象について、再試行できるよう表示を維持する | 同左 |

この表示を組み立てる処理を、`ReservationStatus`にまとめました。次は型の宣言部分です。

```csharp
internal sealed record ReservationStatus(
    string? AlarmText,
    string? ShutdownText,
    string? ShutdownOutcome);
```

各項目の文字列が`null`なら、その行を表示しません。`ShutdownOutcome`には、取消済みの結果や、Windowsに終了を要求した後の案内を入れます。

この型の生成処理では、Windows APIやファイル保存を呼びません。予約とコントローラーの状態から表示内容を作る処理にして、状態ごとの結果を検証できるようにしています。[表示判定の実装](https://github.com/JaehongLIM2/alarm_program/blob/86faa68bdd246ec04025ffa1583b27d90b42164b/src/WindowsAlarm/Services/ReservationStatus.cs)

画面側は、その結果を受け取って表示を切り替えます。次は実装の抜粋です。

```csharp
ShutdownText.Text = status.ShutdownText;
ShutdownReservationRow.Visibility = status.ShutdownText is null
    ? Visibility.Collapsed
    : Visibility.Visible;
```

`Collapsed`は表示しないだけでなく、レイアウト上の場所も確保しない値です。予約がないときに、空白の行が残らないように使っています。[MicrosoftのVisibilityの定義](https://learn.microsoft.com/en-us/dotnet/api/system.windows.visibility?view=windowsdesktop-10.0)

なお、設定欄と予約済みの内容が異なる状態は、この設計でも存在します。予約行には登録した内容を表示し、予約変更には再予約が必要だという関係を明確にする必要があります。

## 設定を無効にしても、取消操作は使えるようにする

アラーム再生中や、アラーム開始後の自動終了待機中には、設定欄と通常の実行ボタンを無効にしています。途中で別のテストや予約処理が始まらないようにするためです。

ただし、取消ボタンまで同じ無効化の対象に入れると、操作したい場面で使えなくなってしまいます。

実際のXAMLでは、取消行を、設定の有効・無効に連動するコンテナーの外側に置いています。以下は構造を示す抜粋で、配置属性を省略し、ボタン名を日本語に置き換えています。

```xml
<StackPanel>
  <!-- 表示条件は予約状態から決める。設定の無効化には連動させない -->
  <Grid x:Name="ShutdownReservationRow">
    <Button Content="PC自動終了を取り消す"
            Click="CancelShutdown_Click" />
  </Grid>

  <StackPanel IsEnabled="{Binding IsEnabled, ElementName=SettingsPanel}">
    <Button Content="アラームをテスト" Click="Test_Click" />
    <Button Content="設定を保存" Click="Save_Click" />
    <Button Content="アラームを設定して休止状態にする"
            Click="Hibernate_Click" />
  </StackPanel>
</StackPanel>
```

無効になったWPF要素はヒットテストやフォーカスの対象にならず、入力イベントの発生元にもなりません。見える位置にボタンを置くだけでなく、操作可能な状態かどうかも確認しました。[MicrosoftのUIElement.IsEnabledの説明](https://learn.microsoft.com/en-us/dotnet/api/system.windows.uielement.isenabled?view=windowsdesktop-10.0)

今回の変更前も取消ボタンは設定の無効化から分離されていました。配置を変えることで、その性質を失わないことが今回の確認事項です。「以前は取消ボタンが使えなかった」という不具合を修正したわけではありません。

また、自動終了時刻の表示は「終了予定」から「終了確認予定」にしました。たとえば8時に確認を始め、その後にカウントダウンや利用中の確認を挟むのであれば、8時に即座に電源が切れるような表現を避けたかったためです。

## 取消に失敗したとき、ボタンを消してよいのか

予約がなくなったら行を隠す、という処理には例外が必要でした。

アラーム予約の取消では、アプリ内の状態を変更するだけでなく、取消状態のファイル保存と、Windowsに登録した予約タスクの削除を行います。

その途中で失敗すると、状態が一致しない場合があります。

| 成功した処理 | 失敗した処理 | 残る問題 |
| --- | --- | --- |
| アプリ内の状態変更・タスク削除 | 取消状態の保存 | ファイルに古い予約状態が残る可能性がある |
| アプリ内の状態変更・取消状態の保存 | Windowsのタスク削除 | Windows側に予約タスクが残る |

どちらも「すべて取り消せた」と表示してよい状態ではありません。

既存の処理は失敗を報告し、再操作による取消の再試行に対応していました。しかし、新しい表示処理でアプリ内の`Cancelled`という状態だけを見て行を隠すと、その再試行の入口を消してしまいます。

そこで、取消を完了できていないかどうかを、表示側から確認できるようにしました。

```csharp
var removed = TryRemoveTask();
WakeCancellationNeedsRetry = !persisted || !removed;
```

`persisted`は取消状態の保存結果、`removed`はタスク削除の結果です。どちらかが失敗していれば、予約のフェーズが取消済みでも、状態文と取消ボタンを残します。

PC自動終了の取消でも、現在の実行中は終了を取り消せたが、その状態をファイルに保存できなかった場合には、保存未完了として再試行できる表示を維持します。

```text
取消を操作
  ├─ 必要な処理が完了 → 状態を更新し、該当する行を隠す
  └─ 保存・タスク削除が未完了 → エラーを表示し、再試行操作を残す
```

これらは、実使用中にファイルやタスクの障害が起きたという報告ではありません。**条件付きでボタンを隠す変更が、既存の失敗時の操作を壊さないか**を、検証で確認したものです。[取消処理の実装](https://github.com/JaehongLIM2/alarm_program/blob/86faa68bdd246ec04025ffa1583b27d90b42164b/src/WindowsAlarm/Services/AlarmCoordinator.cs)

処理結果やエラーの表示領域は、予約行とは別に残しています。行が消えたことだけを、処理完了の通知にはしていません。

ただし、Windowsへ実際の終了要求を出した後は、アプリ内で取り消せる段階ではありません。その場合はPC自動終了の取消ボタンを表示せず、以後の操作はWindowsの終了画面で行う案内に切り替えます。

## 表示を直したあと、ロック解除時の動作も見直した

ボタンの説明を「音を止めても自動終了予約は残る」にそろえても、実際の操作経路が同じ意味になっているとは限りませんでした。

11月3日の検証記録には、アラーム開始後に復帰通知やセッション変更通知を受けると、停止ボタンを押す前にPC自動終了が取り消される問題が残っています。以前の実装では、開始直後30秒の例外を除く復帰通知と、セッション変更を取消の理由にしていました。

```text
アラームが鳴る
  ↓
音を止めるためにWindowsのロックを解除する
  ↓
セッション変更の処理が、自動終了を取り消す
  ↓
停止ボタンを押すころには、終了予約が残っていない
```

停止ボタンの処理だけを読めば、終了予約は維持しています。しかし、実際にはそのボタンへ到達する前に別の処理が予約を消していました。「停止しても予約は残る」という画面の説明だけでは、この違いを説明できません。

そこで、復帰・セッション変更の通知だけで直ちに予約を取り消す処理を見直しました。セッション変更は利用の兆候として記録し、元の終了確認時刻を維持します。その時刻になったら利用中の確認へ進み、60秒間応答がなければ終了を取り消します。

```text
ロック解除 → 音を停止 → 終了予約と取消ボタンは残る
                              ↓
                     予定時刻に利用中の確認
                              ↓
                     応答がなければ終了を取消
```

予約を維持することと、利用中のPCを無条件に終了することは分けています。明示的な取消、アプリ終了、実際の再スリープなどで進行中の自動終了を取り消す処理は残しました。遅れて届く復帰通知や繰り返し通知も検証対象にしています。[修正コミット](https://github.com/JaehongLIM2/alarm_program/commit/86faa68bdd246ec04025ffa1583b27d90b42164b)

UIを確認するときには、ボタンを押した直後だけでなく、そこへ至る操作も含める必要があると分かりました。今回なら「ロック解除して、音を止める」が一つの流れでした。

## ウィンドウを閉じる操作にも、残るものがある

もう一つ、停止や取消と混同しやすいのが、メインウィンドウを閉じる操作です。

| 閉じるときの状態 | 閉じた後の扱い |
| --- | --- |
| まだ始まっていないアラームを予約済み | 未来のアラームと、その予約時の設定を維持する |
| アラーム再生中、または開始後の自動終了待機中 | 再生を止め、進行中の自動終了を取り消す |

未来のアラームはWindowsタスクスケジューラに登録されているため、メインウィンドウを閉じただけでは消しません。予約をなくしたい場合には、閉じる前に「アラーム予約の取消」を使います。

これは、YouTubeプレイヤーのウィンドウを閉じる動作とも異なります。そちらはアラーム停止と同じ処理につながり、開始済みの自動終了予約は維持します。単に「窓を閉じる」と書かず、どのウィンドウかも区別する必要がありました。

設定カードには、メインウィンドウを閉じると進行中の自動終了は取り消され、未来のアラームは残ることを表示しています。この関係は、画面と[終了時の処理](https://github.com/JaehongLIM2/alarm_program/blob/86faa68bdd246ec04025ffa1583b27d90b42164b/src/WindowsAlarm/Services/AlarmCoordinator.cs)を照合しました。

## 見た目と状態遷移を分けて確認する

開発時の検証記録とテストコードには、状態から作られる表示と、実際のWPF画面の両方を確認する手順が残っています。記事を書くにあたって、それらを実装と照合しました。

| 確認したこと | 方法 |
| --- | --- |
| 予約の有無・自動終了の設定に応じた表示 | 予約スナップショットとコントローラーの状態を与えて確認 |
| 音を停止した後も自動終了を取り消せる | 停止済み状態と、終了待機・カウントダウン・利用中の確認待ちを組み合わせて確認 |
| 入力欄の変更で既存予約の取消ボタンが消えない | 予約表示を設定した後、画面の自動終了トグルをオフにして確認 |
| 保存失敗後も再試行できる | 状態ファイルの置換が失敗するように開き、解除後の再試行と保存結果を確認 |
| タスク削除失敗後も再試行できる | 失敗を返すテスト用スケジューラーを使い、再試行と、復旧時の再試行フラグも確認 |
| 設定を無効にしても取消ボタンは有効 | 実際のWPF画面で`IsEnabled`を確認 |
| 小さいウィンドウやスクロールでも取消操作が残る | 最小サイズの560×640で、表示位置と操作可能な状態を確認 |
| ロック解除してから音を止めても終了予約が残る | セッション変更通知と停止処理を順に呼び、予定時刻・保存状態・表示を確認 |

UIの検証では、実際のメインウィンドウへ検証用の予約表示を与えています。この表示確認のために、本物のアラームを予約したり、PCを休止・終了させたりはしていません。

10月27日のUI変更時の記録は、基本回帰検証69件成功・失敗0件です。11月3日の予約維持修正後の記録は、74件成功・失敗0件です。いずれも音声制御・予約・復旧などを含む件数で、UIだけの件数ではありません。WPF画面のテストには、通常サイズと最小サイズの画像を保存する処理もあります。[検証コード](https://github.com/JaehongLIM2/alarm_program/blob/86faa68bdd246ec04025ffa1583b27d90b42164b/tests/WindowsAlarm.Tests/Program.cs)

今回の原稿作成では、これらのテストやGUI操作を再実行していません。また、11月3日の検証では電源APIをテスト用の代替実装に置き換えており、修正後の物理的なS4復帰・ロック解除・実際のPC終了を確認した結果ではありません。コード上の状態遷移と実機の確認範囲は分けています。

## 今回の配置で、まだ気にしていること

予約があるときだけ行を表示するため、予約や取消によって下部の高さは変わります。また、予約状態を固定領域に置いた分、小さい画面では設定欄のスクロール量が増えます。

今回は、設定を一度に多く表示することより、予約中の取消操作をスクロールせずに見つけられる配置を選びました。ただし、これが使いやすくなったことを、誤操作率や操作時間で測定したわけではありません。

音を停止してもPCの自動終了が残る、という動作自体も、説明と状態表示を必要とします。今後の実使用で、停止後の表示から次の動作を判断できるかは引き続き確認したい部分です。

今回、自分で操作の意味を確認し直したことから、名前・配置・表示条件・失敗時の再試行まで見直すことになりました。次に似た画面を作るときには、正常に予約できた画面と同時に、停止後や取消に失敗した画面も並べて確認したいと思います。

実装と今回の確認範囲は、[UI変更・検証記録](https://github.com/JaehongLIM2/alarm_program/blob/86faa68bdd246ec04025ffa1583b27d90b42164b/docs/UI_STYLE.md)にも残しています。
