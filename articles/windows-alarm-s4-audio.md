指定した時刻にPCは休止状態から復帰した。アプリでは再生処理も始まっている。それなのに、音が聞こえませんでした。

自宅のノートPCでWindowsアラームを試していたときのことです。ロックを解除すると音が聞こえる。しかし、目覚ましとして使うなら、起きてロックを解除する前に鳴ってもらう必要があります。

[最初の記事](https://zenn.dev/nu0044/articles/windows-alarm-tv-inspired)では、知人の家で見たテレビの予約電源をきっかけに、テレビのない自宅でWindows用のアラームを作った経緯を書きました。[前回の記事](https://zenn.dev/nu0044/articles/windows-alarm-reservation-ui)では、予約・停止・取消のUIを見直しました。

今回は、予約したアラームが実際の利用条件で鳴るか、S4復帰後の音声出力を調べた記録です。「復帰した」と「音が聞こえた」の間にあった問題を掘り下げます。

:::message
2026年10月26日の実機確認と、その後の実装・検証記録を、11月12日に整理し、11月14日に公開用に見直した記事です。実機で音が聞こえた記録は当時の.NET 8版に関するもので、移行後の.NET 10版の実機結果とは区別します。本文の実装説明とコード参照はコミット `86faa68` を基準にしています。実装や検証コードの整備には生成AIを利用しました。今回の原稿作成・公開前の確認では、実機試験を再実行していません。
:::

## テストボタンでは再現できていなかった条件

Windows Alarmは、C#・WPFで作ったデスクトップアプリです。Windowsタスクスケジューラに復帰用の予約を登録し、S4の休止状態から戻ったあと、ローカルMP3やYouTubeを再生します。

テストボタンで音を出す場合と、朝のアラームでは、使う状況が違います。

| 確認方法 | そのときの条件 |
| --- | --- |
| 起動中のPCでテストボタンを押す | ユーザーが画面を操作でき、音声出力もすでに使える状態 |
| 予約した時刻にS4から復帰する | 復帰直後で、Windowsはロックされたまま。出力機器の復帰も含めて確認が必要 |

テストボタンで鳴ったことだけを根拠に、翌朝も同じように鳴ると考えることはできませんでした。

このアプリが使うのは、ログイン済みユーザーのセッションです。ロック中もセッションはありますが、ログアウトや、再起動後にまだログインしていない状態は別です。今回調べたのは「ログインしてから休止状態に入り、ロックされたまま復帰する」条件でした。[タスクの実行コンテキストに関するMicrosoftの説明](https://learn.microsoft.com/en-us/windows/win32/taskschd/security-contexts-for-running-tasks)

## 「鳴った」を四つに分ける

無音の問題を考えるうえで、次の段階を分けました。

```text
Windowsが復帰する
  ↓
アラームの処理が始まる
  ↓
プレイヤーの再生時間が進む
  ↓
スピーカーから音が聞こえる
```

アラームとして必要なのは最後の段階です。しかし、ログや自動テストで確認しやすいのは、その手前まででした。

「再生を開始した」というログがあっても、実際に音が出たとは限りません。再生時間が進んでいても、出力先や音量、接続したスピーカーの状態までは、その値だけで分かりません。

調査中には画面を点灯させる要求も試しましたが、このノートPCでは、それだけではロック解除前の無音は解消しませんでした。画面を点灯させる処理と、音声の出力経路を分けて調べる必要がありました。

## ローカルMP3の出力をAlertsに変更した

ローカル音楽については、WPFの再生処理から、Windows Runtimeの `Windows.Media.Playback.MediaPlayer` を使う方式へ変更しました。その際、`AudioCategory` に `Alerts` を指定しています。

以下は現在の[ローカル再生処理](https://github.com/JaehongLIM2/alarm_program/blob/86faa68bdd246ec04025ffa1583b27d90b42164b/src/WindowsAlarm/Services/LocalAlarmPlayer.cs)から、カテゴリと繰り返しに関する設定だけを取り出したものです。ファイルの読み込み、再生開始、エラー処理、破棄処理は省略しています。

```csharp
using Windows.Media.Playback;

var player = new MediaPlayer
{
    AudioCategory = MediaPlayerAudioCategory.Alerts,
    IsLoopingEnabled = true,
    AutoPlay = false
};
```

Microsoftの定義では、`Alerts` は警告用途の音声を表すカテゴリです。アプリが再生する音声の用途をシステムへ伝える設定として使用しています。[MediaPlayerAudioCategoryの定義](https://learn.microsoft.com/en-us/uwp/api/windows.media.playback.mediaplayeraudiocategory?view=winrt-26100)

この変更後、自宅のノートPCでは、S4から復帰してロックを解除する前にもMP3が聞こえることを確認できました。[当時の検証記録](https://github.com/JaehongLIM2/alarm_program/blob/86faa68bdd246ec04025ffa1583b27d90b42164b/docs/VALIDATION.md)

ただし、再生APIとカテゴリを含む出力方式を変更した結果なので、「`Alerts`の一行だけが原因を解消した」とまでは切り分けていません。確認できたのは、**この環境では、出力方式を変えるとロック解除前にも音が聞こえるようになった**ことです。

Windows内部のどの制御が無音を起こしていたのかまで特定したわけでもありません。「Windowsはロックすると通常の音声を必ず消す」「AlertsならすべてのPCで鳴る」という一般的な説明にはしていません。

## 次の調査に使えるログを残す

現在の実装では、メディアを開いたときや音声状態が変化したときに、`AudioStateMonitor.SoundLevel` をログへ記録します。Windowsのセッション変更についても、変更の種類を記録しています。

Microsoftは、`AudioStateMonitor` を使って、システムが音声ストリームの音量を下げたりミュートしたりした状態の変化を検出する方法を説明しています。[音声状態の変化を検出する方法](https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/detect-and-respond-to-audio-state-changes)

次に再現した場合には、少なくとも次の時刻を比較できるようにします。

| 記録するもの | 調べたいこと |
| --- | --- |
| アラーム開始 | 予約した処理が開始されたか |
| メディアを開いた結果・再生時間の進行 | ファイルを開き、再生処理が進んでいるか |
| `SoundLevel` の変化 | システムが報告する音声状態に変化があるか |
| ロック解除などのセッション変更 | 聞こえ始めたタイミングと対応するか |
| 人が音を聞いた時刻 | 実際の利用結果がどうだったか |

これらは原因を調べる材料です。`SoundLevel` の値が正常に見えることも、スピーカーの前で音を聞いたことの代わりにはなりません。

## MP3が鳴っても、YouTubeは別の出力経路だった

ローカルMP3の問題が改善しても、WebView2で再生するYouTubeの音声は、同じ変更では改善しませんでした。

```text
ローカルMP3 → アプリが作るMediaPlayer → Alerts

YouTube    → WebView2内のプレイヤー → ブラウザー側の音声出力
```

MP3用の `MediaPlayer` に設定したカテゴリが、別のプレイヤーにも適用されるわけではありません。同じアプリの中にあっても、どこが音を出しているかを分けて確認する必要がありました。

開発記録には、WebView2内の動画からWeb AudioでPCMを受け取り、Windows側のAlerts出力へ渡す実験も残っています。2026年10月26日の実機記録では、このノートPCでロック解除前にYouTubeの音が聞こえています。

記録された出来事の順序は次のとおりです。表はログ原文の転載ではなく、検証文書の要約です。

| 時刻 | 記録された出来事 |
| --- | --- |
| 22:18:14 | Alertsへの音声転送を開始 |
| 22:18:18 | アプリの再生確認条件を満たした |
| 22:20:39 | Windowsのロックを解除 |
| 22:20:43 | アラームを停止 |

この順序は、ロック解除前に処理が進んでいたことを示す材料です。音が聞こえたという結果は、別途行った実際の聞き取り確認に基づいています。[実機確認の記録](https://github.com/JaehongLIM2/alarm_program/blob/86faa68bdd246ec04025ffa1583b27d90b42164b/docs/VALIDATION.md)

一方、この音声転送は、公式IFrame Player APIのPCM取得機能を使ったものではありません。YouTube側の変更に影響される実験的な処理です。また、YouTubeの開発者ポリシーには音声・映像の分離や変更、ユーザーに表示されていないバックグラウンドプレイヤーでの再生に関する禁止事項があります。[YouTube Developer Policies III.I](https://developers.google.com/youtube/terms/developer-policies#i.-additional-prohibitions)

動いたという実験結果を、そのまま一般向けに推奨できる実装とは扱っていません。公開配布に向けた方式と機能範囲には見直しが必要です。ローカルMP3の出力改善と、この実験の評価は分けて考えています。

## 再生に失敗したときの音も用意する

無音の原因を調べることに加えて、再生できなかったときにどうするかも必要でした。

現在の[再生制御](https://github.com/JaehongLIM2/alarm_program/blob/86faa68bdd246ec04025ffa1583b27d90b42164b/src/WindowsAlarm/Services/AlarmPlaybackService.cs)は、YouTubeが指定されていれば再生確認を待ち、失敗したらローカル音楽へ切り替えます。YouTubeを指定しなければ、最初からローカル再生へ進みます。

```text
YouTubeの再生確認
  ├─ 確認できた → 継続して監視
  └─ エラー・時間切れ → YouTubeを停止してローカルMP3へ
                                           ↓
                              ファイルなし・再生失敗
                                           ↓
                                  生成したWAV警告音
```

YouTubeの開始時は最大20秒、確認後は再生進行や音声出力を10秒間確認できない場合に切り替えます。これはアプリの判定条件であり、実際の聞き取りを保証する時間ではありません。[判定処理](https://github.com/JaehongLIM2/alarm_program/blob/86faa68bdd246ec04025ffa1583b27d90b42164b/src/WindowsAlarm/Services/YouTubePlaybackHealth.cs)

切り替えるときは、先にYouTube側を停止・破棄します。数秒後にMP3も鳴らすだけでは、YouTubeの開始が遅れたときに音が重なるためです。古い再生から遅れて通知が届いても、切り替え後の状態を戻さないようにしています。

ローカルMP3も、指定したファイルが消えていたり、開けなかったりする可能性があります。その場合はコードで生成したWAVをAlerts経由で再生し、その経路も失敗した場合には `SoundPlayer`、Windowsの警告音へ順に切り替えます。

ただし、出力装置そのものが使えなければ、音源を何段階用意しても鳴る保証はありません。代替の音源を用意することと、物理的な出音を確認することは、両方必要でした。

## 自動テストで確認したこと、耳で確認したこと

検証記録を読み返すと、「音声テスト成功」という一つの言葉では範囲が広すぎると感じます。

| 確認の種類 | 確認できること | それだけでは分からないこと |
| --- | --- | --- |
| 再生制御のテスト | 失敗時の切り替え、停止順序、遅れた通知の扱い | 実際の音声装置から音が出るか |
| 実際のMediaPlayerを使う統合テスト | 再生時間の進行、繰り返し、停止など | S4復帰後のロック中に人が聞けるか |
| PCMの検証 | 無音ではないデータを受信しているか | スピーカーまで届き、聞こえるか |
| S4から復帰させた実機確認 | そのPC・設定・版でロック解除前に聞こえたか | 別のPCや更新後の版でも同じか |

10月26日のローカルAlerts統合検証では、再生の進行や停止を音を出さない設定で確認しています。その後、実機でロック解除前にもMP3が聞こえたことを確認しました。YouTubeのPCM検証も、データとプレイヤーの進行を調べた自動テストと、人が音を聞いた確認を分けて記録しています。

アラームの停止処理も重要です。再生に失敗したときに音を出す工夫だけでなく、停止後に遅れて音が始まらないことまで、再生制御の検証対象にしています。

## 現在の配布物で、もう一度確認したいこと

実機で音が聞こえた記録は.NET 8版のものです。その後、プロジェクトは.NET 10へ移行しました。

移行時の別環境では、音声関連の統合検証が5件失敗しています。同じ環境で.NET 8版を比較しても同じ5件が失敗し、点検プロセスから見える出力装置数は0でした。この比較は、.NET 10版の音声動作が成功したことを示しません。[.NET 10移行時の検証記録](https://github.com/JaehongLIM2/alarm_program/blob/86faa68bdd246ec04025ffa1583b27d90b42164b/docs/NET10_MIGRATION.md)

その後の記録には単一EXEのAPI・リソース診断などもありますが、S4復帰直後のロック中に、実際に音が聞こえたという確認とは別です。

次の実機確認では、使用するEXEの版、Windowsと出力装置、音量設定を記録したうえで、ローカルMP3を使って次の流れを確認したいと考えています。

1. 通常起動中に再生と停止を確認する。
2. 自動終了を無効にして、近い時刻のアラームを予約する。
3. S4から復帰したあと、ロックを解除する前に音が聞こえるか確認する。
4. 聞こえた時刻と、復帰・再生・セッション変更の記録を照合する。
5. ロックを解除して停止し、音が止まることと停止後の音量を確認する。

これは今後の確認手順であり、今回実行済みの結果ではありません。

## アラームの成功は、再生開始のログより先にある

この問題で分かったのは、PCを復帰させること、プレイヤーを動かすこと、実際に音を聞けることを、一つの成功として扱わない方がよいということでした。

手元のノートPCでは、ローカル音声の出力方式を変えることで、ロック解除前にも音が聞こえるようになりました。同時に、その結果からWindows全体の原因を断定したり、新しい配布物でも検証済みだと考えたりはできません。

目覚ましとして必要なのは、朝、まだPCを操作していない自分に音が届くことです。テストボタンを押したときの成功から、実際に使う条件での成功まで確かめることが、このアプリでは大事でした。
